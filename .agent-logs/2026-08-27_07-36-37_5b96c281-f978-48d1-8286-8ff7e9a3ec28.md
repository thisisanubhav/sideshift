**Config file changed:** [.claude/settings.json](.claude/settings.json)

```json

      "command": "python3 \"$CLAUDE_PROJECT_DIR/.claude/hooks/capture_agent_log.py\" prompt" }] }],
```

**Script:** [.claude/hooks/capture_agent_log.py](.claude/hooks/capture_agent_log.py)

- `UserPromptSubmit` hands the script the prompt verbatim. It is written verbatim.
- `Stop` hands the script only `transcript_path`. The script reads that JSONL,
  walks it backwards to the last assistant message carrying text, and writes

  blocks**, so no reasoning, no tool calls, no file reads, no diffs land in the log.
- One file per session, `YYYY-MM-DD_HH-MM-SS_<session-id>.md`, in the format the
  brief specifies. Frontmatter `total_exchanges` and `last_prompt_time` are
  rewritten on each append.

**Log location:** `.agent-logs/` — committed, and explicitly *not* in `.gitignore`
(verified with `git check-ignore`).

## 4. What I tried first that did not work

**`hash(text)` for the Stop-hook dedup guard.** The `Stop` event can fire more
than once per turn, so the script keeps a digest of the last response written and
skips a repeat. I used Python's builtin `hash()`. It failed the moment I tested it
across three separate process invocations: `PYTHONHASHSEED` is randomised per
process, so every run produced a different digest and every run appended a
duplicate `RESPONSE` entry. Test showed 2 entries where 1 was wanted. Replaced
with `hashlib.sha256`, retested, 1 entry.

**Dedup state file written into `.agent-logs/`.** First version dropped a
`.last-<session-id>` marker next to the log. That directory ships with the repo
and should contain the log and nothing else, so the state moved to the OS temp
directory.

**A zsh footgun that made me misread a test.** My cleanup line was
`rm -rf "$T/.agent-logs" /tmp/claude-agentlog-*.sha`. The glob matched nothing, and
zsh's `nomatch` aborts the whole command rather than passing the pattern through —
so `rm` never ran, the test executed against stale state, and I briefly thought the
sha256 fix hadn't worked. It had. Re-ran with the cleanup fixed.

**Verification before wiring anything up.** I pipe-tested the raw script with a
synthetic transcript containing a thinking block, an intermediate `"Let me check
that."` text block, a `tool_use` block, and a final answer — then grepped the
output to confirm only the final answer survived. It did; the string planted in the
thinking block appears zero times.

**"No silent declines" is a CHECK constraint, not a form rule.**
`(status = 'declined') = (decline_reason is not null)`. The database refuses to
store a decline without a reason. Product fix #2 cannot be bypassed by any client.

**Expiry is lazy, not scheduled.** `expire_stale_applications()` is called on the
reads that care instead of standing up pg_cron. Same observable behaviour, no
infrastructure. Trade-off: an application that lapses while nobody is looking
flips the moment someone looks. Documented in the README.

**`brand_responsiveness` is a definer-rights view.** Under RLS a creator can only

**Threads are one route for both roles** (`/t/[id]`), not `/b/threads/[id]` and

**A creator could approve their own deliverable and release their own payment.**

```sql
if v_owner is null or v_owner <> v_brand_id then raise ... end if;
```

For a creator, `v_brand_id` is NULL. `v_owner <> NULL` is **NULL, not true**, so the OR is NULL, the branch never fires, and the guard silently passes. `request_changes` had it too.

## What it does

A **4px bar down the left edge** of any card representing a relationship. For an application inside its response window, **the bar is the window**:

```
fill = remaining / 48h,  recomputed every second from the real expires_at
```

Not an animation on a loop — `initialMs` comes from the server so the first client render matches exactly, then it ticks. In the screenshot:

| Applicant | Remaining | Strip |
|---|---|---|
| `@hana.pours` | `00:40:39` | **tally-live**, ~1% — a red stub |
| `@the.slow.kitchen` | `08:59:39` | **tally-standby**, ~19% — an amber bar |

You can see which one is about to be lost without reading either number. That's the whole argument.

**Under six hours it switches to `tally-live`** — at that point it isn't "pending" any more, it's "about to be lost".

**Top-anchored** rather than bottom. A bottom-anchored bar shrinks away into the corner of the card; top-anchored keeps the remaining window beside the creator's name, where the eye already is.

**Reduced motion** is handled by construction: the transition is `motion-safe:` only, so the bar sits at its correct static fill rather than easing to it.

## The real problem I had to solve

Google authenticates people. It does **not** say which side of a marketplace they're on. Left alone, `handle_new_user()` defaults every Google signup to `creator` — so a brand clicking "Continue with Google" would silently land in the creator app. That's precisely the ambiguous state this whole product exists to prevent.

So: **the role is chosen on our page first**, carried across in a 10-minute httpOnly cookie, and claimed on return by a new `claim_role()` function. It's a **one-shot** — it refuses once the account has any campaigns, applications or threads, so it can't be replayed later to switch sides and inherit someone else's work.

On the sign-**in** page there's no role, because an existing account keeps the side it already has.

## Two migrations

- **`0007_oauth_role_claim.sql`** — `claim_role()`, deliberately not an UPDATE policy on `profiles`.
- **`0008_unique_handle_for_oauth_signups.sql`** — hardening I found while thinking it through: Google supplies no handle, so the trigger derives one from the email local part. `maya@gmail.com` and `maya@studio.co` would **collide on the UNIQUE constraint** and the second signup would die with a raw Postgres error. A local part can also contain `+` or `-`, which the `handle_shape` CHECK rejects outright. It now sanitises, de-duplicates with a numeric suffix, and keeps Google's real name and avatar — which the old trigger threw away.

Both applied to the live database.
